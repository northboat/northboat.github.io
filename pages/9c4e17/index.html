# AI 产品概述

# 熵增

ToC 产品和技术是两回事，既不割裂也不强相关，好的技术不一定产出好的产品，好的产品也不一定依赖绝对好的技术，技术达标 + 用户体验 = 好的产品

相应的，如果用户体验不行，这个产品总是不能称之为好，除非有垄断的技术领先

以 toC 的文档服务为例，传统的文库，无非提供存储、下载、搜索等服务，然后通过“卖文档”实现盈利，这之中有两个关键问题

  • 搜索质量：用户是否需要动用大量精力才能搜到想要的内容
  • 文档质量：用户找到的文档是否值得花钱购买

这类产品的核心竞争力，说白了就是用户能否从你的文档库获到值得付费的文档内容

但在 AI 时代，搜索的门槛被拉的很低，只需要用一个文本框，一个 query，大模型就能给出一大堆回答，这里不得不考虑一个问题，用户是否还会为“人工搜索、手动筛查、付费下载”这套逻辑买单？ —— 2025 百度的广告收益下降 16 个点

如何立足于“存储”发扬 AI 功能，是 PSIG 是否能存活并增长的核心，这里有两个发展方向，一个是依靠存储发展个性化的 AI（例如提供个体 AI 如 OpenClaw 的记忆服务），一个是依靠存储发展 toB 的 AI 服务（类似于 Saas，但这一套似乎并不奏效），随着智能体的发展，用户 PC 端的使用量显著上升，甚至超过疫情时期的下载量，这充分说明当前 AI 对用户使用习惯的改变，显然电脑更适合与 AI 交互，以将算力转化为可以看得见的生产力，依据云存储提供个性化的 AI 记忆服务是一个很好的点子

耦合 AI 底座和业务逻辑

  • 通过 MCP 将复杂的业务处理能力提供给智能体，智能体通过策略分发找到对应的 MCP 工具，实现一次处理并返回用户，这里是一个嵌套的功能，业务逻辑需要 AI 功能来实现，上层的智能体调用 MCP 获取业务逻辑，实现 AI - Service - AI 的架构
  • 也就是说，现在与用户交互的不再是死板的接口，而是一个个智能体，智能体通过预设的 prompt 调用相应的 MCP 获取具体的业务操作，并返回给用户；也可以理解为，从前的 routes 路由实现的业务分发，被智能体调用 MCP 的方式取代了，当然，调用智能体仍然使用某一接口如 /chat 触发

# 自我进化

Robin 看来，「AI能做事只是第一步；能不能判断自己有没有把事情做好，才是效率真正被打开的关键」，如果 AI 验证没做好的话，AI 就会重新迭代、优化，这就形成了一个闭环。这个闭环中如果几乎没有人干预，效率就会很高。目前，已经有伐谋这类工具，基于这个“闭环”的思路帮助许多企业提效，但在更多的场景下，由于目前的工具还不足够成熟，仍然需要依赖人脑来构建这样的闭环，并想办法让 AI 能够验证自己的工作做得好还是不好

再次重申，上次提过的「希望业务不要训模型，业务训模型是一个熵增的过程」，原因首先是资源层面的。训练模型本身非常耗费算力，而当前行业整体算力依然紧张，卡资源十分珍贵。如果各条业务线都分散去训练自己的模型，不仅投入巨大，也会削弱整体竞争力。而且模型的评估是个很难很复杂的事儿，业务团队往往并不擅长对模型做全面、准确和长期有效的评估。有可能自己训了一个模型短期看效果不错，但实际上再过一个月就会发现效果并没有那么好

更关键的是，这样被训出来的模型，极易被基础模型的升级能力所覆盖。这样的结果，就是团队陷入“训一轮、追一轮、再训一轮”的恶性循环，最后做了很多无用功。相比之下，业务更应把精力投入到产品和应用层面，把模型能力真正转化为用户价值和业务结果

2B、2C 和 2P，这次他又做了一轮澄清

  • 2B 是企业付费
  • 2C 单指靠广告赚钱的模式
  • 2P 指的是个人付费

Robin 还跟大家传递了一个理念，希望「用 coding 解决所有的问题」。目前普遍的做法还是“机做人审” —— 让 AI 去做事，人来把关、做一些必要环节的 check；再往后的趋势，很可能就是“不允许人 coding”了，这个观点虽然现在听起来比较激进，但如果类比很多其他领域，就会发现在很多事儿机器来做更加精确，并不是人的长项

模型驱动三层架构

  1. Genflow：与用户直接交互，实现工作流编排
  2. MCP：为 Genflow 提供具体业务能力
  3. Strategy：提供例如转码、存储和 AI 等策略接口

文库、橙篇、自由画布场景下 AI 助手对话流程

  1. 用户输入指令
  2. 意图识别、风控
  3. 策略分发
  4. 业务逻辑
  5. 返回 SSE 流

# GenFlow 状态机

通过事件驱动状态机实现 PPT 生成流程，这是 makeppt 的上层 genflow 的“管控”工作，利用 Golang 库 FSM 实现 PPT 状态流转的有向无环图

  • looplab/fsm: Finite State Machine for Go (opens new window)
  • fsm package - github.com/looplab/fsm - Go Packages (opens new window)
  • Go 每日一库之 134：fsm 基有限状态机库 (opens new window)

在状态机模型内，我们不需要在业务代理判断状态，而只定义规则，关注点完全在

  • 源状态（source）
  • 事件（event）
  • 目标状态（target）

不符合规则状态转移路径由状态机引擎自动拦截

// 初始化状态机
func (g *genflow) initFsm() {
    g.fsmClient = fsm.NewFSM(
        FsmStateInit,
        fsm.Events{
            {Name: FsmEventInit, Src: []string{FsmStateInit}, Dst: FsmStateQueue},                                                                       // 初始化阶段
            {Name: FsmEventModelChoice, Src: []string{FsmStateQueue, FsmStateExecute, FsmStateReason, FsmStateRoundDispatch}, Dst: FsmStateModleChoice}, // 选择工具事件
            {Name: FsmEventReason, Src: []string{FsmStateModleChoice}, Dst: FsmStateReason},                                                             // 执行思考模型事件
            {Name: FsmEventRoundDispatch, Src: []string{FsmStateReason, FsmStateExecute, FsmStatePause}, Dst: FsmStateRoundDispatch},                    // 工具调度
            {Name: FsmEventExecute, Src: []string{FsmStateReason, FsmStateModleChoice, FsmStateRoundDispatch}, Dst: FsmStateExecute},                    // 调度事件
            {Name: FsmEventSingleMessage, Src: []string{FsmStateExecute, FsmStatePause}, Dst: FsmStateSingleMessage},                                    // 单意图输出message
            {Name: FsmEventChat, Src: []string{FsmStateModleChoice, FsmStateExecute, FsmStateRoundDispatch, FsmStatePause}, Dst: FsmStateChat},          // 对话事件
            {Name: FsmEventCancel, Src: []string{
                FsmStateExecute,
                FsmStateModleChoice,
                FsmStateReason,
                FsmStateChat,
                FsmStateRoundDispatch,
            }, Dst: FsmStateCancel}, // 取消事件
            {Name: FsmEventTimeout, Src: []string{
                FsmStateExecute,
                FsmStateModleChoice,
                FsmStateReason,
                FsmStateChat,
                FsmStateRoundDispatch,
            }, Dst: FsmStateTimeout}, // 超时事件
            {Name: FsmEventCompleted, Src: []string{FsmEventInit, FsmEventCancel, FsmStateChat, FsmStateExecute, FsmStateSingleMessage}, Dst: FsmStateCompleted}, // 完成事件
            {Name: FsmEventError, Src: []string{FsmStateExecute,
                FsmStateModleChoice,
                FsmStateReason,
                FsmStateChat,
                FsmStateRoundDispatch,
                FsmStateSingleMessage},
                Dst: FsmStateError,
            },
        },
        fsm.Callbacks{
            // 进入queue状态
            fmt.Sprintf("enter_%s", FsmStateQueue): func(ctx context.Context, event *fsm.Event) {
                resource.LoggerService().Notice(ctx, "fsm statusChange", logit.AutoField("fsm", event))
                g.queued()
                <-g.initCompleteCh

                go safely.RunVoidContext(g.ctx, func() {
                    g.SaveLongTermMemory(g.ctx)
                })
            },
            fmt.Sprintf("before_%s", FsmStateInit): func(ctx context.Context, event *fsm.Event) {
                resource.LoggerService().Notice(ctx, "fsm statusChange", logit.AutoField("fsm", event))
                // 先判断是否存在临时记忆，如果存在，则从临时记忆输出
                // useTempMemory := false // todo 控制是否使用临时记忆
                // if !useTempMemory {
                //     return
                // }
                g.hasMemory = g.OutputFromRedis()
                if g.hasMemory { // 直接返回
                    g.memoryEnd <- true
                    // _ = g.fsmClient.Event(g.ctx, FsmEventCompleted)
                } else {
                    // 风控处理
                    go safely.RunVoidContext(g.ctx, g.risk)
                    // 初始化取消逻辑
                    go g.judgeHitCancel()

                    go safely.RunVoidContext(g.ctx, func() {
                        g.pauseMonitor(g.ctx)
                    })
                }
            },
            fmt.Sprintf("after_%s", FsmEventInit): func(ctx context.Context, event *fsm.Event) {
                resource.LoggerService().Notice(ctx, "fsm statusChange", logit.AutoField("fsm", event))
                // 进入选择工具的事件
                _ = util.SafeFSMEvent(g.ctx, g.fsmClient, FsmEventModelChoice)
            },
            "leave_state": func(ctx context.Context, event *fsm.Event) {
                // resource.LoggerService().Notice(ctx, "fsm statusChange", logit.AutoField("fsm", event))
                resource.LoggerService().Notice(ctx, "leave_state", logit.AutoField("event", event))
                // fmt.Printf("leave_state: %s, %s", event.Src, event.Dst)
            },

            // 进行工具选择状态
            fmt.Sprintf("enter_%s", FsmStateModleChoice): func(ctx context.Context, event *fsm.Event) {
                resource.LoggerService().Notice(ctx, "fsm statusChange", logit.AutoField("fsm", event))
                // 选择工具
                var streategyInfo genflowtypes.ToolChoicesResponse

                // 添加中间预处理的逻辑
                hasPreProcess := g.preProcess()
                if hasPreProcess {
                    streategyInfo.ModelType = g.information.Base.ModelType
                } else {
                    streategyInfo = g.modelToolChoices()
                }
                g.businessDetection(g.ctx, []openai.ChatCompletionMessageToolCall{}, "chat")

                if g.isPauseFlag {
                    select {
                    case <-ctx.Done():
                        resource.LoggerService().Notice(ctx, "fsm continue signal ctx done")
                        break
                    case <-g.continueSignalCh:
                        resource.LoggerService().Notice(ctx, "get continue signal")
                        time.Sleep(100 * time.Millisecond)
                        break
                    case <-g.continueWithChoiceCh:
                        resource.LoggerService().Notice(ctx, "cancel_end_flag")
                        time.Sleep(100 * time.Millisecond)
                        return
                    case <-g.continueWithDispatCh:
                        resource.LoggerService().Notice(ctx, "cancel_end_flag")
                        time.Sleep(100 * time.Millisecond)
                        return
                    }
                }

                if streategyInfo.ModelType == 0 {
                    if err := util.SafeFSMEvent(g.ctx, g.fsmClient, FsmEventError, gerror.ErrorCodeModelError, "model_choice error"); err != nil {
                        resource.LoggerService().Warning(g.ctx, "fsm error", logit.Error("err", err))
                    }
                    return
                }

                if g.information.Base.IsSimple {
                    // if err := g.fsmClient.Event(g.ctx, FsmEventChat); err != nil {
                    //     resource.LoggerService().Warning(g.ctx, "fsm error", logit.Error("err", err))
                    // }
                    //fsm panic处理
                    if err := util.SafeFSMEvent(g.ctx, g.fsmClient, FsmEventChat); err != nil {
                        resource.LoggerService().Warning(g.ctx, "fsm error", logit.Error("err", err))
                    }
                } else if g.information.Base.ModelType == modelTypeSingle {
                    // g.toolChoiceResponse.Scene = ScenePcSearch
                    if g.hitsFullSingleOutput() {

# 状态机启动

状态机一经初始化，就会自动执行到终止节点，所谓自动状态机的含义就是如此，在以下代码中，首先初始化了状态机，而后通过 util.SafeFSMEvent(g.ctx, g.fsmClient, FsmEventInit) 触发状态机的第一个事件，于是开启自动化流程

// Run 执行生成流处理任务
//
// 该方法初始化用户请求信息，设置30分钟超时上下文，并异步执行主处理逻辑。
// 返回一个事件通道用于接收处理过程中的状态和结果。
//
// 参数:
//    ctx     - 上游上下文，用于传递请求上下文信息
//    req     - 运行请求参数，包含对话消息、频道信息、用户ID等
//    httpReq - HTTP请求对象，包含原始HTTP请求信息
//
// 返回: chan resource.Event - 事件通道，异步返回处理过程中的各种事件
func (g *genflow) Run(ctx context.Context, req genflowtypes.RunReq, httpReq ghttp.Request) chan resource.Event {
    // 初始化用户请求信息
    g.req = req
    g.wpURIParamsExtra(ctx, httpReq, req)
    g.ctx, g.ctxCancelFunc = context.WithTimeout(logit.CopyAllFields(context.Background(), ctx), time.Minute*30)
    // 29min55S 会超时
    g.backendTimeoutTimer = time.NewTimer(time.Minute*29 + time.Second*55)
    g.upstreamCtx = ctx
    g.httpReq = httpReq
    
    // 执行一系列初始化，包括状态机的初始化
    g.init()

    // 异步执行任务
    go safely.RunVoidContext1(g.ctx, g.run)
    return g.outch
}

# 双 channel 流水线

输出不是一条 channel 直接怼到 HTTP，而是分成两级，中间挂一个独立协程做转运：

channel 类型 容量 职责
sendCh chan outputMessage 100000 业务侧产出：FSM 各状态把帧写进来
outch chan resource.Event 100000 对外输出：Run() 把它返回给 HTTP 层 range

容量开到十万是刻意的选择——生成 PPT 时 tool_call_info 会连发数百帧，任何一级阻塞都会导致丢帧，宁可占内存也不能让发送缓冲区满。

sendToOutCh 就是夹在中间的轮询器，init() 里用 go safely.RunVoidContext(g.ctx, g.sendToOutCh) 常驻：

// 伪码：把业务帧从 sendCh 搬运到 outch，顺带处理暂停/保活/结束
func (g *genflow) sendToOutCh(ctx context.Context) {
    for {
        // 数据帧、暂停信号、保活定时器、结束信号多路 select
        select {
        case <-ctx.Done():
            return

        case frame := <-g.sendCh:
            if g.isPauseFlag {
                // 暂停期间不吐数据帧，改发 ping 维持连接
                g.outch <- g.pingFrame()
                continue
            }
            g.outch <- frame

        case <-g.pauseSignalCh:
            g.isPauseFlag = true
            g.outch <- g.pauseFrame()   // pause 帧，status=pause_user / pause_system

        case <-g.continueSignalCh:
            g.isPauseFlag = false
            // 从断点续传，不重头跑：靠 continue:{messageID} 里记录的 next_step 定位
            g.resume(g.getContinueData(ctx))

        case <-g.keepaliveTimer.C:
            g.outch <- g.pingFrame()    // id:7 那种 data:{} 的帧
            g.keepaliveTimer.Reset(KeepaliveTimer)

        case <-g.backendTimeoutTimer.C: // 29min55s
            g.outch <- g.endFrame(StatusTimeout)
            return
        }
    }
}

# 两类暂停语义的统一恢复

暂停有两种来源，表面看是两套接口，本质收敛到同一个轮询器：

类型 常量 触发 pause 帧 status 恢复方式
用户主动暂停 PauseTypeUser = 1 用户点暂停 → /pause pause_user 用户点继续 → /message
工具阻塞待补充 PauseTypeSystem = 2，PauseSubTypeToolStop = 2 大纲生成完，等用户确认"生成 PPT" pause_system 用户提交确认 → /message 带 next_step

两者走的是同一条路径：

  1. 标记：pause.go 调 SetPauseData，在 Redis ZSet pause:{chatID}_{queryID} 里 ZAdd 一个唯一 key（score 是时间戳），并把详情写进这个 key，g.isPauseFlag = true。
  2. 发帧：轮询器看到 isPauseFlag，往 outch 塞 pause 帧，前端停止渲染数据帧。
  3. 续传标记：/message 把续传数据（message_id、类型、next_step）写进 continue:{messageID}，过期一年，再投递 continueSignalCh。
  4. 恢复：轮询器收到信号，清 isPauseFlag，从 ZSet 里定位断点继续执行。这就是为什么每次 chat 不是从头开始，而是靠 queryID/chatID 从断点续跑。

用 ZSet 而不是简单 string 存暂停标记，是为了支持"按时间取最早一个暂停点"（ZRangeByScoreWithScores ... Count: 1），并且同一会话可以有多个暂停记录待处理。

# pauseMonitor：把散落的 select 收敛成独立协程

上面是设计意图。落到代码里，真实的暂停判断原本是散在 FSM 各状态内的——modelToolChoices、dispatch 等处都各写一遍 if g.isPauseFlag { select {...} }，等 continueSignalCh / continueWithChoiceCh / continueWithDispatCh。重复的 select 既难维护，也容易漏掉某个分支。

把这些 signals 抽象出来，收进一个独立的 pauseMonitor 协程，就是这套机制的干净表达：

// 伪码：根据散落在 FSM 各状态的 isPauseFlag + select 片段抽象，
// 不是逐字源码。pauseSignalCh 投递暂停，三类 continue channel 按
// 续传粒度分别投递，monitor 统一裁决是放行业务还是挂起等待。
type pauseKind int
const (
    pauseUser      pauseKind = iota // 用户主动
    pauseToolStop                   // 工具阻塞待补充
)

func (g *genflow) pauseMonitor(ctx context.Context) {
    for {
        select {
        case <-ctx.Done():
            return

        // 统一入口：无论哪种暂停，都先查 ZSet 标记、发 pause 帧
        case k := <-g.pauseSignalCh:
            key, need := g.checkNeedPause(ctx)
            if !need {
                continue
            }
            g.isPauseFlag = true
            g.outch <- g.pauseFrame(k) // k 决定 status 是 pause_user 还是 pause_system

        // 三类续传：统一清 flag、从 continue:{messageID} 恢复
        case <-g.continueSignalCh:       // 通用续传
            g.resume(g.getContinueData(ctx))

        case <-g.continueWithChoiceCh:   // 续传后重新做模型/工具选择
            g.restoreToolChoice()
            g.resume(g.getContinueData(ctx))

        case <-g.continueWithDispatCh:   // 续传后直接派发下一步（如补大纲跑 makeppt）
            g.restoreToolDispatch()
            g.resume(g.getContinueData(ctx))
        }
        g.isPauseFlag = false
    }
}
