# TDD Vibe Coding

From Coder to Builder

Vibe Coding 本质就是自然语言驱动 LLM 直接产出可执行代码（Prompt Engineering），软件从 “工程实践” 退化成 “一个想法”，AI 是编程的义肢，并且随着 Agent 的不断发展，人逐渐编程 AI 的义肢，二者的主导关系在慢慢变化，AI 越来越主动

事实上，产品给我们提需求实际上也是一种 VIbe Coding（什么碳基 Agent）

程序员本质上是把现实需求转变为数字世界的语言描述的“翻译者”，在 AI 的帮助下，“翻译”工作变得越来越简单（这也是外界不看好这份工作会持续的原因），未来程序员的意义更多在于翻译的信达雅以及现实需求本身的完善，而不是仅仅做好“翻译”这件事 —— 相信 AI 的不断发展，这样的品味优势也会逐渐削弱

TDD 测试驱动设计是较为规范的 Vibe Coding 方式，通过提前定义验收条件，驱动 AI 开发功能，面向测试编程

  • 在 TDD 里，人类天然可以充当 QA，完成 AI Coding 的质量闭环

但在实际工程场景中，测试用例总是在开发之后、上线之前，从顺序上还是自上而下的 PRD 开发，而非面向测试开发 TDD。当然，这不意味着 TDD 不好，只是在开发之前，作为 RD 需要去对齐产品和测试验收标准，这需要一定的嗅觉

让测试和验证成为开发过程的核心，这是不可避免的趋势

另外，对于已有代码库，最好的 Vibe 方式是保持已有代码的品味和清洁，让 AI 根据已有代码进行编码 —— AI 很擅长模仿而不善于创造

# Spec Coding

少写 Prompt，多用规则

规约编程（Spec Coding），或者说规范驱动编程（SDD，Spec-Driven Development），强调在动手编写代码之前，开发者与 AI 需先共同制定一套关于软件架构、功能边界与业务逻辑的详细规约文档，AI 将严格基于此文档逐点执行开发任务，旨在将 AI 编程从“玄学”拉回“工程学”

原则 解决什么问题
编码前思考 错误假设、隐藏困惑、缺少权衡
简洁优先 过度复杂、臃肿抽象
精准修改 无关编辑、触碰不应碰的代码
目标驱动执行 通过测试优先、可验证的成功标准

Rules：约束智能体的需求文档，统一放在项目根目录的 .rules 文件夹中，说白了就是规范 LLM 行为的文档形式的 System Prompt，在以下四个方面对 LLM 进行提示与约束

  • What：代码库干嘛的
  • Where：目录结构如何组织
  • How：场景流程，few shot
  • Should/Not：应该/禁止做什么

可以参考 Cursor 内置的 Rules，本质上都是一段 markdown 格式的 System Prompt，让 AI 先阅读指定文件再进行操作，进行相对规范的操作

  • 单测 rule：unit-test-rules
  • 代码风格 rule：code-style
  • Go 单测 skill：go-unit-test

还有一种比较极端的 Spec 方式，直接用 Lint 规则、类型系统和架构约束把不合理的写法直接禁掉

# Pairing Coding

结对编程最早是 ACM 里的概念，一人编码，一人审查，在结对编程中，编码和审查的角色是随时互换的 —— Comate 厂内的 Copilot

人机协同十二原则

  1. 用注释加强 AI 代码理解：先写注释再编码
  2. 代码人易懂 ＝ AI 易懂，提升代码可读性：保持代码风格；有意义的命名；代码块粒度合适（150 行左右）；先搭架子再填空
  3. 留心 AI 能力范围：AI 后台运行，需要定时检查
  4. 准备私域知识：如优质的 few shot、RAG 等
  5. 编码前多提问：了解 AI 意图，明确个人需求
  6. 编码后 AI 审查：让 AI 审查 AI 代码
  7. 写代码前先澄清：清晰代码意图和功能
  8. 让 AI 复用和扩展个人能力：插件、MCP、Skills
  9. 专注于核心业务，杂活全部交给 AI：如复杂的正则表达式
  10. 不会的、不熟悉的让 AI 帮忙
  11. 人是驾驶者，AI 是辅助手
  12. 接受 AI 的不完美

常见场景

  • 基于注释生成代码（Comment Driven Coding）
  • 根据代码生成注释
  • 充当搜索引擎
  • 单测文件生成

# Harness 工程

后训练正在摧毁 Harness

Rules 通过规则 Prompt 约束 Agent 行为，属于 SDD，Harness 通过严谨的环境条件限制 Agent 行为，属于 BDD

  • SDD（Specification Driven Development）是一种以规范为核心、先写规范再生成代码的开发方法，强调AI辅助下的高效、可控和可追踪的软件开发流程
  • BDD（Behavior-Driven Development）是一种以业务需求为导向的软件开发方法，通过自然语言描述系统行为，促进开发、测试和业务团队的协作

AI Coding 的演化一定是：SDD（rules） → BDD（harness） → DDD

# 可复用技能

MCP：模块化的、标准化的、微服务化的工具调用（function call），让 LLM 快速获取某项技能，包括但不限于搜索网页、生成文档、读写文件

Skill：本质上是渐进式披露的 Markdown 系统提示词，虽然现在还没有明晰的概念提出，但是 Skill 已经明显区分为两类

  • 一种是环内的 skill：给 agent loop 的 skill
  • 一种是环外的 skill：与人交互的 skill

Skill 与 MCP 区别：MCP 需要 JSON-RPC 协议接入并且一次暴露整个 MCP 能力，而 Skills 直接让 LLM 读取 Markdown 文档获取，通过“渐进式披露”提供能力，并且 Markdown 文档较于 MCP 调用更具普适性

├── SKILL.md # 定义、描述 skill
├── scripts/ # 具体的可执行代码脚本，其说明在 SKILL 中定义
├── templates/ 文档模板
├── resources/ 资源文件

# ACE 工程

ACE 上下文工程：解决上下文腐烂

  • 上下文工程 ≠ 精炼总结，压缩 ≠ 总结
  • 压缩可逆，总结不可逆，总结的信息丢失程度远大于压缩，就像 Hash 和 Zip
  • kv cache 和 prompt cache？前缀缓存

节省上下文小妙招

  1. 图检索代替 grep：用 CodeGraph 代替全文 Grep 检索，减少 Agent 阅读代码时的 Token 消耗，和 LSP 代替 Grep 的思路类似
  2. 脚本复用：让 Agent 沉淀可执行的脚本，如”构建单测脚本“，让”任务执行“本身成为一种可复用的能力
  3. Agent 的动态工具选择：枚举配置工具名，根据 skill 注入 mcp 工具，用 31B 的小模型决定加载哪些 skill，JEV 和 Decision API 就是这个道理

# A2A 到智能组织

“找到摸鱼的方法实现长期主义”

Agent 之间的通信，通过通信共享内存（桥接）还是共享内存通信（总机）？

  1. 对于 Go 编码者而言，显然通信是更符合直觉的选择，优雅高效，在实践中也确实节省 Token，不需要重复的上下文堆叠
  2. 共享上下文本质上就是 ReRead，这里的操作空间在于，子 Agent 是隔离的，可以用便宜模型，这样也可以实现节省，并且能更大程度上保留语义

Agent 的内存即上下文 context，在控制 Token 总量相同的前提下，很难量化二者的实际工程效果，更多需要根据隔离性和任务复杂度适当的选择桥接还是总机

这可以引申到另一个争论，即是 Multi Agent 还是 Agent as a Tool，前者对应通信的 A2A 模式，后者对应共享内存的“调用”模式（将子 agent 作为工具调用），优缺点和 Agent 通信大差不差，同样具体问题需要具体分析，到底谁更好尚无定论

此外，Graph Engineering 是较火的 A2A 方向，旨在将不同智能体的按照领域划分进行组合联系，构成图的协同工作结构，这是更上层的架构设计

在实践中，可采用 DSH + Pi 实现第二种方式的 A2A（Agent as a Tool），DSH 作为需求沟通和任务调度的主题，Pi 作为任务执行的主体，作为 Tool 供前者调用

  • Pi：极简的 Harness 工程实践，依赖强模型，本质上是少了教 Agent 如何去干活的提示词，假设 —— 模型已被后训练训成"知道怎么当 agent"，system prompt 大半是在重教它已经会的东西。上下文相比于 CC 少一个数量级，同样的窗口装得下更多真实代码

# 递归自我改进

数据是 LLM 的血液，RSI（Recursie Self-Improvement） 的重点在于“数据闭环” —— 构建一套血液循环系统

数据闭环是自编译的艺术，例如

  • AnyDev 开发与优化：通过配套的 agent + workspace + skill 承接真实需求，需求分析 → 人工审核 → 拉分支开发 → 联调 → 人工 PR → MR → 更新 skill
  • “工单” Agent：工单场景的数据闭环，agent 创建工单 → 人工标注有误的工单 → 优化 rag 知识库 → 继续创建工单

Loop 和 RSI 的区别

  • codex 的 goal 模式是经典的 loop 实践，让 agent 在 loop 中持续发现、解决问题，实现工作 - 复查闭环
  • 递归式自我改进是当前 Loop Engineering 的核心，我们不满足在 loop 中解决问题，还需要在 loop 中改进方法

这里引申到另一个议题，即长时序智能体（long-horizon agents）的优化，通过减少决策轮次来提供任务成功率和上下文长度：[2609.02042] Act More, Decide Less: Skill-Guided Adaptive Action Chunking for Long-Horizon LLM Agents (opens new window)

# 工作区和访问控制

一个基本的控制访问思路实践是：给每个基建开放只读权限 + Loop + 人工介入实现 Bug 的全链路追查

  • 只读 KubeConfig
  • 只读 MySQL 账号
  • 只读 Redis 账号
  • 日志 Cli
  • 只读 Git 权限

工作区只隔离环境，但不隔离操作 —— 只要有网络和权限，理论上 agent 可以在任意环境去读写 DB，agent 确实是需要访问控制管理的，这涉及到密码工程，当然在工程实际里，这大概率退化成管理问题

这里更多想讨论的是 Workspace 的具体形态，CubeSandbox - 容器、micro-VM 还是完整 VM (opens new window)

  1. Agent 跑在容器里，例如在 Docker 容器里跑一个 Pi，再对外暴露
  2. Agent 跑在容器外，把 Docker 容器作为一个长期资源分配给 Agent 调用操作
  3. Workspace 以 Sandbox、云函数的形式提供给 Agent 调用
