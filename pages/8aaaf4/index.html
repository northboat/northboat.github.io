# Training: Crypto-Caesar Ⅰ

简单的古典密码解密，给定一串码

PDA MQEYG XNKSJ BKT FQILO KRAN PDA HWVU ZKC KB YWAOWN WJZ UKQN QJEMQA OKHQPEKJ EO BWCYZILHHNKW
1

合理猜测每个字母加上一个相同的数变为当前码，如A+2=C, Z+1=A

于是编写程序列出总共26种可能性，同时将大写转小写便于阅读

python 代码

code = "LZW IMAUC TJGOF XGP BMEHK GNWJ LZW DSRQ VGY GX USWKSJ SFV QGMJ MFAIMW KGDMLAGF AK YZJJKAKWUUKH"
i = 0
while i < 26:
    print(i+1, end='.')
    for c in code:
        if c == ' ':
            print(c, end='')
            continue
        print(chr(97+(ord(c)-65+i)%26),end="")
    i += 1
    print('\n')

# BurpSuite 抓包重放

通过 BurpSuite 对网络请求进行抓包

Burp Suite Professional 是一套来自 PortSwigger，用于测试 web 安全性的高级工具集，从一个基本的拦截代理到尖端的 Burp 扫描器

  • Burp Suite Professional 2025.12 for Windows x64 - 领先的 Web 渗透测试软件 (opens new window)
  • Download Burp Suite Community Edition - PortSwigger (opens new window)

入门：BurpSuite 安装及使用实操 - 刑之风 - 博客园 (opens new window)

BurpSuite 测试流程

  1. 设置端口代理
  2. 抓包
  3. 重放

基本思路：在 Burp 设置 Proxy 拦截，然后把浏览器/程序/应用写一个代理发到 Burp 的 Proxy 上，Burp 将作为一个中转站进行网络通信，这样就能对每个 HTTP 进行数据抓包

首先在 Burp 的 Settings → Tools → Proxy 中设置代理127.0.0.1:8080

若是 Spring 程序，可以在启动类前设置代理

public static void setProxy(){
    System.setProperty("http.proxyHost", "127.0.0.1");
    System.setProperty("http.proxyPort", "8080");
    System.setProperty("https.proxyHost", "127.0.0.1");
    System.setProperty("https.proxyPort", "8080");
}

public static void main(String[] args){
    ProxyUtil.setProxy();
    SpringApplication.run(AuditAiAgentApplication.class, args);
}

# HTTPS 与 TLS 协议

HTTPS = HTTP + SSL / TLS

众所周知，HTTP 是建立在 TCP 基础上的应用层协议，TPC 通过三次握手在服务端和客户端之间建立长连接（在 HTTP1.0 之后），通过超时重传、确认帧来保证可靠传输

而三次握手并不存在身份认证，他仅靠累加的 ACK 码来确认握手双方的回应，这会造成

  • 客户端无法认证服务端身份，任意一个服务器可以伪造响应来欺骗客户端，例如，攻击者可以搭建一个伪造网站（如模仿银行官网），并让用户的 HTTP 请求指向该伪造站点获取用户敏感信息
  • HTTP 没有机制确认传输的数据是否完整，攻击者可在传输过程中随意修改数据包内容，接收方无法察觉数据已被篡改，无法抵抗中间人攻击

HTTPS 在电商与支付兴起的背景下应运而生，其本质上是一个组合协议，由 HTTP 实现数据可靠传输，SSL / TLS 实现身份安全认证，HTTPS 连接的建立顺序如下

  1. TCP 三次握手
  2. TLS 握手
  3. HTTP 加密传输

在实际应用中，HTTPS 引入密钥协商、对称加密、数字证书、哈希摘要等技术来保证数据隐私、身份可信以及消息完整性，具体而言

  1. 使用非对称加密 + 对称加密的混合加密机制，如采用 RSA/ECC 进行密钥协商，AES 进行加密传输
  2. 利用数字证书证明服务端可信：服务器需要向权威的证书颁发机构（CA）申请包含自身身份信息的数字证书，客户端（浏览器）在建立连接时，会验证服务器证书的合法性：若证书无效（如伪造、过期），浏览器会弹出安全警告，提醒用户 “该网站不安全”
  3. 消息认证机制保证消息完整性：服务器会对传输的数据生成哈希摘要，并通过密钥进行签名，接收方在解密数据后，会重新计算哈希值并与签名比对：若不一致，说明数据已被篡改，直接丢弃数据包

# TCP 连接

TCP 报文头部字段

三次握手

四次挥手

  • 客户端：FIN-WAIT-1/2 + TIME-WAIT + CLOSED
  • 服务器：CLOSE-WAIT + LAST-ACK + CLOSED

为什么都是一次请求一次确认，挥手要四次，握手只需要三次？

  1. 握手实际上是服务端在一次发送里同时进行了确认和请求，所以少了一次
  2. 但在挥手时不能这么做，因为需要等待数据传输完，有等待时间，例如 server 收到 FIN 请求后，还有 50KB 数据在传，所以要等传完之后，再发 FIN 请求告知自己不会再传了；此时 client 虽然发了 FIN，但也只是不传输，但仍接收

# SYN Flood 泛洪攻击

TCP 握手 SYN 泛洪攻击（SYN Flood）：TCP 建立连接的三次握手，服务端（被动一方）必须严格按照这个程序来进行，即对客户端始终响应，如果客户端发送 SYN 包企图与服务端建立连接，但发送完 SYN 包后就不管，那会发送什么事情捏

  • 客户端发送一个 SYN 包给服务端后就退出，而服务端接收到 SYN 包后，会回复一个 SYN+ACK 包给客户端，然后等待客户端回复一个 ACK 包
  • 但此时客户端并不会回复 ACK 包，所以服务端只能一直等待直到超时，服务端超时后，会重发 SYN+ACK 包给客户端，默认重试 5 次，而且每次等待的时间都会增加（可以参考 TCP 协议超时重传的实现）
  • 另外，当服务端接收到 SYN 包后，会建立一个半连接状态的 Socket，所以，当客户端一直发送 SYN 包，但不回复 ACK 包，那么将会耗尽服务端的资源，这就是 SYN Flood 攻击

# 安全编码

前面讲"怎么发现代码里的问题"，这里讲"怎么写就不容易出问题"。核心原则：非侵入式——新增需求尽量不改已有逻辑。

# 非侵入式编码

四种手法：

1. 函数变长入参：用 opt ...AllocOperateOpt 代替 args ...string，定义强类型的选项函数（如 WithCollaboratorAuth(envID, role)）。原来调用一行不动，新参数有名字、可读性强。

2. 参数外置/内置：

  • 外置：已有函数不动，外面封装一层 XXXByEnvId，内部查到 username 再调原函数
  • 内置：抽象出底层 QueryThirdPartyTokenByUsername(ctx, origin, deleted, username)，让原函数退化为一行转发 return its.QueryThirdPartyTokenByUsername(..., ctx.UserName())，需求直接调底层函数

3. 配置化编码：配置内容越简单越不容易错。下拉框版本的演进：JSON 对象 → 字符串数组 → 分号分隔字符串 "19.03;26.1"，前端自己 split，避开 json.parse 的风险。

4. Hook 编码：用钩子实现业务逻辑，标准是"不需要项目本体发布就能实现需求"，如网关钩子做日志统计、Java Agent 插桩追踪（注意 Spring AOP 只是侵入式较小，并非真正非侵入）。

# 防御性编程

三个不要：

  1. 不要相信上层输入 / 上游传参
  2. 不要向上层暴露底层信息
  3. 不要相信下游依赖，预留灰度开关兜底

第 3 条的落地：配置中心拉配置 + 后台 if 硬编码判断，命中才返回新字段，前端按开关决定是否展示，回滚只改配置不发版。示例：新增 sshDomain 时用独立的 EnableSshAppId 白名单，与既有功能灰度互不影响，先单 appId 验证再改配置扩量。

# Bug 追查

多服务排障三步：

  1. 先摸清报错原因，链路精确到 pod 级，不接受"admin 到 web-server"这种模糊描述
  2. 按阶段定位——逐段比对日志（哪一段字段丢了就锁定哪一层），配合按 pod id 查配置
  3. 代码与配置并重——只修代码不修配置照样不通
