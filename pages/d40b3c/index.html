Linux in Android

# Termux

Termux 是 Android 上的 Linux 终端

# GNU 工具链

Android 底层同样是 Linux 内核，但上层的用户空间与桌面发行版完全不同，C 库、命令、init、包管理等各成一套

GNU（哥怒）与 Android 的用户空间区别

类别 Android 用户空间 GNU/Linux 说明
C 库 bionic（libc.so 内含 libm/libdl/线程） glibc 精简实现，无 NSS，POSIX 扩展不全
动态链接器 /system/bin/linker64 ld-linux-aarch64.so.1 ELF 的 PT_INTERP 指向不同，二进制不通用
基础命令 toybox（单二进制多命令） coreutils + util-linux 只含常用子集，--help 极简
shell mksh bash 系统默认 sh 是 mksh
init init + *.rc 脚本 + 属性服务 systemd / SysV init 无依赖管理、无 cgroup 编排那套
运行时 ART（执行 dex） 无（直接跑 ELF） 应用层 Java/Kotlin → dex → ART
IPC Binder unix socket、dbus 跨进程调用主要走 Binder
权限模型 每 App 一个 uid + SELinux 域 root/普通用户 + 文件权限 untrusted_app 域，默认无 root，setuid 无效
目录布局 /system /vendor /apex /data /bin /lib /etc /usr 无 /usr、无 /etc/passwd 传统体系
软件分发 APK（pm / installd） apt / dnf / pacman 装的是应用，不是系统软件包

所以 Termux 的工作实际上是，在自己的私有目录里另建一套工具链（把 GNU 工具按 aarch64-linux-android ABI 重编译），再让它们优先

  1. 拿到一块可写可执行的目录：/data/data/com.termux/files/usr
  2. 把“发行版的 /usr”铺进去：usr/bin、usr/lib、usr/include、usr/etc，结构照抄 Linux
  3. 用 Android 的 ABI 编译工具：aarch64-linux-android 交叉编译，链接系统自带的 bionic 和 linker64，rpath 指向 $PREFIX/lib。glibc 那套依赖全部改写成 bionic 能提供的等价实现，缺的部分由 termux-packages 的补丁解决（例如没有 /etc/passwd、没有 NSS）
  4. 让 shell 优先用这套：启动时设 PATH=$PREFIX/bin:$PATH、HOME=$PREFIX/home、LD_LIBRARY_PATH=$PREFIX/lib

具体到输入的 ls

输入 ls
 → shell 按 PATH 顺序找，命中 /data/data/com.termux/files/usr/bin/ls
 → 该 ELF 的 PT_INTERP 是 /system/bin/linker64（系统自带，没换）
 → 依赖的库在 $PREFIX/lib 里（libc 仍是系统的 bionic）
 → 系统 toybox 的 ls 还在 /system/bin/ls，全程没被动过

一条命令从下往上会经过四层

  1. 芯片 / ISA：芯片只会执行指令，“能执行哪些指令”由 ISA（Instruction Set Architecture，指令集架构）规定。ARM64（AArch64）与 x86_64 是两套 ISA，指令编码不通用；同一套 ISA 下不同厂商的芯片（ARM 授权的高通、联发科，Intel、AMD 的 x86-64）二进制通用
  2. 内核 / syscall：内核管内存、进程、文件、驱动，对外只开系统调用一个口。程序读目录必须按编号去调，openat 在 ARM64 上固定是 56。Android 与发行版共用同一个 Linux 内核，二者的 syscall 完全一致，差别只是 Android 用 seccomp + SELinux 收窄了可用的子集
  3. 用户空间：内核之外的一切 —— C 库、命令、编译器、init。程序不直接发 syscall，都经 libc 转一手；Android 用 bionic + toybox，Ubuntu 用 glibc + coreutils
  4. ABI：严格说它不是一层，而是前三层之间的交接格式 —— ELF（linux 可执行文件）头里的解释器路径（PT_INTERP）、依赖的符号名、参数放 x0~x7 还是 rdi/rsi、结构体怎么对齐。ABI（Application Binary Interface）对不上，加载器会直接拒绝

编译器和链接器都是用户空间的工具，按照 ABI 的约定产出二进制。回到 termux 的工作，实际上就是把 GNU 工具重新编译为符合 Android ABI（aarch64-linux-android）的应用，使之可以在 arm64 android 上运行

相对应的，arm64 android 有这几种“跑不了”

现象 问题在哪 为什么 怎么办
Ubuntu ARM64 程序跑不了 ABI PT_INTERP 写死 ld-linux-aarch64.so.1，Android 只有 linker64；硬改路径也不行，还要 glibc 的符号，bionic 里没有 rootfs 提供 glibc 与 ld.so，proot 改写路径让它找得到
x86 程序跑不了 ISA e_machine 对不上，内核直接 ENOEXEC；两套指令编码没有重叠 box64 逐条翻译指令
exe 跑不了 内核 内核不认 PE 格式；Windows 的 syscall（ntdll 调 sysenter 那套）在这里没有实现 Wine 加载 PE 并翻译 syscall 语义 / FEX 翻译 syscall

因为 Android 机器上没有 root 权限，所以这份 Linux 使用了 proot 去 change root，它不动内核、不做虚拟化，只用 ptrace 拦住系统调用（prehook），把路径参数和身份参数改掉，伪装成一个独立的 Linux

对照几个容易混淆的说法

  • 不是模拟器：不解释指令、不虚拟硬件，CPU 和内核都是手机自己的，跑的是 ARM 原生二进制
  • 不是容器：没有 namespace、cgroup 隔离，在系统眼里它就是一个普通的 Termux 进程，ps 里能看到
  • 不是真 root：proot -0 只是把 getuid()/geteuid() 的返回值改成 0，内核仍按 Termux 用户（uid=10xxx）校验权限
  • 实现的两件事：伪造路径视图（相当于 chroot + bind mount）、伪造身份（相当于 fakeroot）；Android 无 root 时 chroot 系统调用直接 EPERM，这才轮到 proot

真正的 chroot() 发生在内核态，需要 root 权限，是在修改根目录指针 fs_struct->root

  • chroot 不是安全边界。它只改路径起点，进程仍共享内核、网络、PID、/proc。经典逃逸手法就是 chroot 后 chdir 出去再 chroot(".")；而且它不改变“进程已经有权限”的事实，所以 chroot 里弄到 root 往往更容易打主机。容器（namespace + cgroup + capability 裁剪）才有隔离语义，chroot 没有
  • 只 chroot() 而不 chdir("/") 也没用。当前工作目录还在旧根之外，ls 一敲就回去了，所以标准写法是 chroot(newroot); chdir("/")

# Mesa 驱动

在 OPPO PLE110（SM8735 / Adreno 825）上启动 Steam，会话 2 秒退出

拷出 session.log ，找到具体的报错信息

TU: error: ../mesa-26.2.2/src/freedreno/vulkan/tu_device.cc:1683:
    device (chip_id = 44030000, gpu_id = 6830) is unsupported (VK_ERROR_INCOMPATIBLE_DRIVER)
[gamescope] [Error] vulkan: failed to find physical device
SDL_Vulkan_CreateSurface failed: ... Failed to create backend.
1
2
3
4
  1. tu_device.cc 是 Mesa 里 Turnip（freedreno 的 Vulkan 驱动） 的源码文件，因此报错的是驱动，并非系统或硬件
  2. is unsupported + VK_ERROR_INCOMPATIBLE_DRIVER 表示驱动查自己的设备表，发现没有这个 chip_id，于是主动拒绝注册。这三层意思分别对应：驱动已加载、驱动能运行、驱动认不出这块 GPU

跟因：Turnip 是 Mesa 的用户态 Vulkan 驱动，靠一张静态设备表把内核上报的 chip_id 映射成 GPU 属性集，当前版本的驱动静态设备表里没有这个 id，驱动会直接拒绝 VK_ERROR_INCOMPATIBLE_DRIVER，因为 拿不一致的参数跑（CCU 分片、tile 对齐、magic 寄存器），错一个就会算错地址，导致花屏、卡死或静默写坏显存

于是完整的报错链为

Turnip 不认 chip_id
 → Vulkan 枚举不到 physical device
 → gamescope 建不出 SDL backend（Vulkan 是硬依赖）
 → exit 1 → 会话结束

拿报错里的 chip_id（44030000）和 gpu_id（6830）去仓库搜 issues

  • #66（closed） (opens new window)：同 chip_id、同 SM8735，维护者给了确定的修法，即换驱动
  • #334（open） (opens new window)：同 chip_id，同类问题仍在跟

新 SoC 上市到 Mesa 收录之间必然有一段时间不可用（驱动静态表查不到），解法只有“换一份设备表里有这块 SoC 的驱动”，于是问题变成找包含 chip_id = 0x44030000 的 Vulkan 驱动

  1. 先看版本：上游 Mesa 主线从哪个版本起加入该 chip_id
  2. 再查补丁：驱动仓库的 patch 脚本里 grep chip_id，能查到这一行才算真支持
# Droid-Deck/Drivers patches/scripts/apply_a8xx_gpus.py
add_gpus([GPUId(chip_id=0x44030000, name="Adreno (TM) 825")], A6xxGPUInfo(CHIP.A8XX, [...]))
1
2
  1. 确认作用于会话那一半：一个驱动包通常分“显示驱动（Android）”和“Linux 半（runtime 运行时驱动）”，Steam 会话用的是 Linux 半。release 说明里要能确认补丁对两半都生效（WinNative 的 Linux 0.1.2 就是 issue 里说的那个版本）
  2. 找到目标驱动：DD-Turnip 与 WinNative · Balanced，两边的 apply_a8xx_gpus 都显式插入了同一个 chip_id

更换驱动

  1. Setup → Components → GPU drivers（第一个 tab），模式从 Auto 改 Matched pair
  2. 选一对（DD-Turnip / WinNative · Balanced），浏览器下 release zip，同页 Advanced → Import 导入驱动对（显示驱动 + Linux 驱动）
  3. 重启 App（显示驱动重启生效），再按 Play

Linux 的 Driver 问题很常见，例如每次都会掉的网卡驱动和永远不适配的显卡驱动
